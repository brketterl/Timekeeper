# Workspace activity history

Admins can open **Activity** in the sidebar to see their workspace's history, newest first. Each event shows what happened, the acting account's name and workspace role at that time, and the date/time in the viewer's local time zone. Load older activity in pages of 50; Refresh shows current entries.

Employees cannot view activity history, including through direct API requests. Backend membership/role checks run on every read; client-supplied workspace IDs cannot select another workspace's history.

## Recorded actions

- Invitations created, accepted, revoked, or replaced. Automatic revocations on employee removal/account-email correction are included.
- Workspace roles changed and membership access removed.
- Employee records and contracts added, changed, archived, or removed; workspace settings changed.
- Timesheet hours submitted, withdrawn, approved, reopened, changed while submitted/approved, or removed. Multiple row transitions of the same type in one sheet/save are grouped, with the period and row count. Ordinary draft hour edits are not logged per keystroke.
- Invoices created, updated, or removed; payments recorded, changed, or removed. Payment entries show the amount/date when applicable; deleting an invoice is recorded as invoice removal, not a separate removal of each child payment.

History begins after deploying this feature. Previous activity cannot be reconstructed. Workspace imports/resets record the resulting detected changes and do not overwrite audit history. The log captures successful committed changes, not denied requests or failed login attempts. Password resets, login/logout, email-provider delivery, account email correction itself, and backup operations are not a comprehensive security/access log in this version.

## Integrity and privacy

Events are generated by backend code from authenticated membership and validated before/after state. API clients cannot supply actor identities or insert/update/delete audit entries. Changes and corresponding events commit in the same transaction; an audit insert failure rolls back that change. No-op saves and rejected writes do not add activity. Snapshots preserve the actor's name/role if their name, permissions, or membership later change.

Database triggers reject updates/deletes to audit entries. This is an append-only application history, **not tamper-proof storage**: a database/server operator could alter the database or drop triggers. The log does not contain raw request bodies, passwords/hashes, invitation/reset tokens, payment references, invoice notes, or full before/after business documents. Event summaries/details are deliberately limited; summaries may be shortened. Names, invitation recipient emails, invoice numbers, dates, payment amounts, and record identifiers are business data and remain private to workspace admins.

There is no automatic deletion/retention policy for history yet. It grows on the existing persistent disk and is included in full encrypted recovery archives. Monitor disk capacity. Workspace JSON exports contain business data only and do not include the relational audit log. Restoring an older full archive returns history/data to that archive's capture point; later events are not retained in the restored copy.

## API

`GET /api/activity` returns `{events, nextCursor}` for the current session's workspace. Pass `?before=<nextCursor>` for older entries. Pages contain up to 50 entries, ordered by descending event ID, with a stable cursor that handles events sharing the same timestamp. Invalid cursors return 400; employees return 403; unauthenticated sessions return 401. There is no write endpoint. Events contain actor ID/name/role snapshots, type, entity ID, summary, structured limited details, and a creation timestamp in epoch milliseconds.

## Local review and release

```sh
git switch staging
git pull origin staging
npm ci
npm test
npm start
```

Use isolated local data/test R2 credentials. Sign in as a local admin, create an invitation or change a contract, and open Activity. Test a submitted/approved timesheet and recorded invoice payment. Confirm the actor and details are correct. Sign in as an employee and confirm Activity is absent. Changes before installing this feature do not appear retroactively.

This adds migration **4** for `audit_events`, its index, and append-only triggers. Existing business records/permissions are retained. Backup tools now support schemas **2, 3, and 4**; schema-4 restores preserve audit entries and clear password-reset tokens/sessions/pending invitations as before.

Before production approval, create a fresh full production recovery archive, download the Cloudflare copy, and verify/restore it locally with the matching key. Keep that pre-migration archive/key. Automated tests exercise old-archive compatibility and preservation of history during restore, but do not replace a production recovery check.

After local review and explicit approval, release main and deploy on the existing Render service. No new environment variables, credentials, email service, or paid instance are required. Confirm the Activity page, admin/employee access boundaries, and successful encrypted backups after deployment.

Rollback: reverting code does not remove migration 4 or its triggers/history. Previous schema-3-only backup tools cannot read schema-4 recovery archives; retain the updated tools or fix forward. Restoring the pre-release database requires a maintenance window and loses changes after its capture; restore into a new directory instead of overwriting a live database.
